# LowTalker engineering notes

Building, signing, releasing and measuring LowTalker. What it is and how to use it is in the [README](../README.md); why it exists is in [PROJECT.md](../PROJECT.md).

## One app

LowTalker is one app. A development build and a release build are the same app under the same names: the bundle identifier `ai.promptctl.low-talker`, one input method, one config file, one chord (Right Option), and port 8610 for its server. They differ in the certificate that signs them and in whether the build may accept connections ("Building" below), so installing either replaces the other. The names are decided in `Sources/Identity/AppIdentity.swift`.

## Building

You need Xcode 16 or later plus `xcodegen` and `jq`, both from Homebrew.

- `make app` generates the Xcode project from `project.yml` with XcodeGen and builds `LowTalker.app` into `DerivedData/`, printing the path, with its input method, `LowTalker Input Method.app`, beside it. It is signed with the development identity ("The development signing identity" below), which it makes first on a Mac that has none, unless `SIGNING_IDENTITY` names another certificate.
- `make package` wraps the app and its input method in an installer package, `LowTalker-offline.pkg`, beside them ("The installer package" below).
- Every build is one of two variants, and `VARIANT` picks which: `offline`, the default, whose app carries exactly the sandbox's entitlements and so cannot reach the network, or `network`, whose app also carries `com.apple.security.network.server` so its server can listen (`make package VARIANT=network`). Nothing else differs, and the input method is the same in both. They share one bundle identifier, so installing either replaces the other; the package's name, read off the app's signed entitlements, says which it is.
- `make install` builds the package and installs it with `sudo installer`: the app into `/Applications` and its input method into `/Library/Input Methods`, replacing whatever LowTalker stood there. A package is the only way the app is installed, since it does not install its own input method.
- `make run` installs the app and launches it. Launch it with `open` and never by running `Contents/MacOS/LowTalker` from a shell: macOS files the menu bar icon under the app responsible for the process, which for a direct start is the terminal, and shows it only while the terminal is allowed in the menu bar. A direct start hands itself to LaunchServices and exits, saying so on stderr. Ten seconds after launch, the log's `menubar` category says whether the icon came on screen. When it never did, the app says so in an alert.
- `make test` makes the development identity ready, since the insertion tests sign with it, then runs `xcodegen generate`, `swift test` and the license gates ("What a release ships, and under what license" below). Generating comes first because the suite reads the project and the plists XcodeGen writes rather than generating them itself, so a bare `swift test` on a fresh clone fails those cases.
- `make gate-replay` replays the speech gate in `Utterance` over the bench fixtures and reports, against master's gate, five things: the speech lost after white-noise bursts and ESC-50 coughs, sneezes, knocks and claps beyond what as much digital silence loses; what changed in those soft readers alone and beside that silence; background talk let in 24 to 36 dB under a speaker; bench variants whose handed samples changed; and what a tap left open keeps of a room. Master's rows are `scripts/gate-replay/baseline.tsv`. A change to the gate quotes the report in its pull request, then runs `make gate-replay-baseline` in its last commit, so the committed baseline is always master's. The ESC-50 clips are CC BY-NC, so they are fetched from one pinned commit into `.build/gate-replay` and never committed. `make test` builds the replay and reports it skipped.
- `make clean` removes the generated project, `DerivedData/`, and `.build/`.

CI runs `make test` and `make app` on a macos-15 runner for every pull request to master and every push to master; the workflow is `.github/workflows/ci.yml`.

## The transcription server

The network build of the app serves transcription with the model it already holds for dictation, so a caller costs no second copy in memory. It answers OpenAI's `POST /v1/audio/transcriptions` and its Realtime transcription socket, `ws://.../v1/realtime?intent=transcription`, at port 8610, on loopback unless the config's `[serve]` table names an interface and a token (see the config below). So a Pipecat `OpenAISTTService` pointed at the base URL the menu's Server line shows, or an `OpenAIRealtimeSTTService` pointed at the same URL as `ws://` plus `/realtime`, transcribes through it. Audio that never reaches the -40 dBFS audible floor, such as a hold where nothing was said, is answered as OpenAI answers audio with nothing said in it: an upload with 200 and empty text, a committed turn with an empty transcript. An upload asking for `response_format=verbose_json` gets one segment with its `id`, `start`, `end` and `text`, though not the `seek`, `tokens`, `temperature` or `no_speech_prob` OpenAI's shape also gives, which this server cannot know, and with Whisper's two scores for dropping a reading: `avg_logprob`, the mean of the words' log probabilities, and `compression_ratio`, which catches a decoder repeating itself, as it can over noise primed with a prompt, sure of every word. The socket streams a turn's words as deltas while its audio is still arriving and answers each commit with the transcript; it takes 24 kHz PCM16, as the spec requires, and only turns the client commits, so `turn_detection` must be null. It transcribes up to four uploads at once and holds up to four sockets open, answering any more of either with a 429, which Pipecat retries for an upload and not for a socket, so a pipeline whose socket is refused stops transcribing. A socket keeps reading while its turns wait for the engine, as they do behind a dictation hold, so a busy engine delays its transcripts, which come in the order the turns were committed. It refuses an upload holding over fifteen minutes of audio, or an append that would take what a socket holds past fifteen minutes: the audio of its turns not yet transcribed, and a second for each turn. So an engine that stays behind a socket's audio ends in refused appends, which Pipecat takes as fatal. Silence alone never does: Pipecat appends through the quiet between turns and commits only when its VAD hears a turn end, so after seven and a half minutes uncommitted the socket starts the turn over from its newest three and three quarter minutes. The turn it replaced is never answered; the one the client commits has its own deltas and transcript. Each request is one line of JSON in the unified log under the `serve` category. `scripts/conformance check <base URL>` judges it against the contract Pipecat holds OpenAI to.

Serve Transcription in the menu switches it on; it is off until someone switches it on, and while it is off nothing listens. The menu's Server line, under the model's, says what it is doing: `off`, `listening at http://127.0.0.1:8610/v1`, or `stopped` and why, when the address is taken or the config cannot be read. Until the model is ready it answers 503. The offline build has no network entitlement, and its menu has no Server line and no switch.

### The model store

`model-tool` keeps the model in `~/Library/Application Support/low-talker/hub`, the store `make app` copies each bundle's model out of, laid out the way the Hugging Face hub lays out its cache. A model is two parts: its weights, under `models/argmaxinc/whisperkit-coreml/<variant>`, and the tokenizer they decode with, under `models/openai/whisper-<size>` and shared by every model of that Whisper size. `model-tool download` installs the default Whisper model (about 632 MB) into it and records a manifest of each part's files and the sizes huggingface.co lists for them at the revision, `installed/<model>.json` for the weights and `installed/tokenizer/<model>.json` for the tokenizer. Every load checks both manifests against the files before it reads them.

    make model-tool                          # builds .build/debug/model-tool, which the build runs and nothing installed does
    .build/debug/model-tool status           # where the model stands; exits 1 unless installed
    .build/debug/model-tool download         # install it, or finish an install that stopped

A download from huggingface.co fetches both parts at one revision: the weights at a whisperkit-coreml commit and the tokenizer at a commit of its openai repo. `model-tool revision` asks huggingface.co which commits `main` names now and prints them as `<weights>-<tokenizer>`; `model-tool download --from <that>` fetches the parts it lacks at exactly those commits, and a plain `model-tool download` fetches at whatever `model-tool revision` would print when it starts. A part the store already holds whole is kept, whichever commit it came from.

A part whose manifest is missing or no longer verifies is taken again, and a part that verifies is left alone. A download that stopped part way leaves no manifest, so the model reads as missing and the next download resumes it: the hub client skips every file already on disk that its own sidecar marks as downloaded. A listed file that is no longer there as recorded reads as damaged, and so does a manifest that no longer parses; `model-tool download` repairs either. Before it takes a part it deletes every file on disk that is not the size the source lists, the hub for a download from huggingface.co and the source's manifest for any other, and after it fails unless every listed file is there at that size: the hub client never hashes a file it finds on disk, so a truncated file, even one copied in from another cache before any manifest existed, would otherwise pass. A store written before the tokenizer had a manifest reads as damaged, "the tokenizer is not installed", and `model-tool download` from huggingface.co records the tokenizer already on disk, fetching only the files that differ at the revision; from a published base it downloads the archive for the tokenizer in it. Two downloads may both start an install into one store; the second waits for the first. Pass `--models-dir` to any of these subcommands to use a different directory.

By default a missing part comes from huggingface.co. `--from` on `model-tool download` names another source, so a network that blocks that host still has a way to a model:

    .build/debug/model-tool pack --to dist                              # dist/<model>.zip, from this store
    .build/debug/model-tool download --from https://example.com/models/  # fetches <base>/<model>.zip
    .build/debug/model-tool download --from /Volumes/LowTalker/hub       # copies from another store

`model-tool pack` writes the archive a published base serves: a store holding that one model, both parts and their manifests and nothing a hub client left beside them. A `--from` beginning `http://` or `https://` is such a base; the archive is downloaded, unzipped beside the store, and read as a store. Anything else is a directory holding a store, and only the files its manifests list are copied, after those manifests verify there. A base that answers anything but 200, or a store that does not hold the part whole, is an error naming the URL or the part. Measured on 2026-09-16, the default model packs to 477,836,162 bytes, and a store with outbound network denied except to localhost installed it from a local base, reported it installed, and transcribed with it.

Every bundle carries its model and loads it in place, a development build included. `make app` copies it out of this Mac's store, `~/Library/Application Support/low-talker/hub`, into `DerivedData/model-store` and build that into the bundle; `scripts/sign-release` fetches the default model into a store of its own and builds that one in instead. Either way it lands at `Contents/Resources/model-store`, where the code signature seals it with the rest of the app. The app loads the model straight from there, read-only: it writes no model data outside the bundle and never creates `low-talker/hub` for it, so a first launch with the network off needs nothing it did not ship with, deleting the app leaves nothing behind, and `codesign --verify` still passes. It rides inside the bundle rather than beside the app on the disk image, because dragging the app to Applications leaves behind anything that sat beside it. A bundle built with no store (`make app BUNDLED_MODEL_STORE=`, which is how CI builds) says at launch that it carries no model, and downloads nothing. A bundle whose store does not hold the model whole stops the load with the reason, and downloads nothing. Measured on 2026-09-16, the release bundle is 625 MB. Loading a carried store whose files are unwritable — the store the code signature seals is read-only on disk — installs nothing and takes no lock: the load and its first transcription both succeed straight off the read-only store. A carried weight file changed by one byte fails `codesign --verify`. What loading in place costs after an update is "Load times and the Neural Engine cache" below.

That the app downloads nothing is a fact of what it links, not of what it calls. Everything that writes a store — the download from huggingface.co or a published base, the copy from another store, `model-tool pack` — is `Sources/ModelInstall`, a module only `model-tool` links; the app links `LowTalkerCore`, which can only read a store and load it. `AppLinksNoInstallerTests` reads Package.swift and project.yml and fails if any product the app links reaches that module. The app does link WhisperKit, whose vendored hub client stays in the binary; what this removes is every path of low-talker's own to it.

### Load times and the Neural Engine cache

Loading the model means Core ML compiling it for this Mac's Neural Engine, which takes minutes for the default model. macOS caches the result, keyed by the model's path, the files that sit there, and the **code-signing identifier** of the process that loaded it, and evicts the cache after an OS update. Replacing the files at a path it had already compiled — which is what an app update does to a model carried in the bundle — misses the cache as surely as moving them. Measured on an M2 Max with the default model; the smaller models in the table under "The latency harness" compile and load faster:

| Situation | Load |
|---|---|
| First load of a model, after an OS update, or after the store moved or its files were replaced | 1.5 to 4.5 minutes |
| Same signing identifier, same files, model already compiled | 1.5 to 7 seconds |
| A binary with a new signing identifier | 2 to 4 minutes again |

The app's identifier is its bundle id, set by its certificate signature, so `make app` builds keep the cache warm on their own.

A release that carries its model pays this compile on its first launch — a model just shipped has never been compiled here — and loading it in place pays it again after every update, because replacing the app rewrites the model files at their path and the cache does not follow them. This is the cost the copy had been hiding: a model copied into Application Support outlived an app update untouched, so an update relaunched warm; a model loaded from the bundle is replaced along with the bundle, so the first launch after each update is cold again. Measured on 2026-09-16 on an M2 Max, loading the default model from a fixed path with the command-line tool this repo then had: 171 s cold the first time, 2.1 s once the cache was warm, and 180 s again after the model files at that path were replaced with an identical copy — the update. While the model is not yet ready, the menu bar icon is an hourglass, described to Accessibility as "LowTalker: preparing the model", and the menu's model line is the one the log records, "loading model, minutes the first time on this Mac, 0 s so far" while it loads and "ready (large-v3-v20240930_turbo_632MB) after ..." once it is resident, counted from launch, with a second line meanwhile saying a press made now is heard once the model is ready. A load that fails draws a warning triangle. A press, held or toggled, draws a waveform while it is open, described as "LowTalker: listening", whatever the model's state; from key-up until every ended press's outcome is reported the icon is a text cursor, "LowTalker: transcribing", once the model is ready, and before then the hourglass, because a press ended during the load is waiting on it. The same press puts a small panel low on the screen, which never takes the focus and lets every click through to what is under it: "Listening" with what the model has read of the press so far, wrapped over up to four lines that keep the newest words in view, then "Transcribing", gone once the outcome is reported. When an insert fails, the panel says why and holds the words that reached no cursor until a click into a text field takes them, its Insert button, there while LowTalker is listening and no press is open, places them at the cursor in front, or a click on the circle at its top-left corner dismisses them. The menu's Bring Back Dismissed Words puts the last dismissal back in the hold, ahead of any words held since; a later dismissal replaces it. If a press is open, they come back once it has been inserted. Words that may have landed anyway, sent with no answer or handed to an app that had not yet taken them, are held and shown too, but a click into a text field does not offer them, since that is how they would be typed twice; Insert places them with the rest. What the panel holds, and the last dismissal, are saved at every change to `low-talker/held.json` in the app container's Application Support. A quit, a crash or an upgrade therefore leaves it held, and the next launch shows it again. A file that cannot be read back is moved aside beside it, and the menu names where; a save that fails is a menu line too, and the file it could not replace is removed, so a launch offers words already placed only when that removal fails as well, which the menu then says. Held words on their way to an app when LowTalker ends are held at the next launch as words that may have landed, and the panel says so. A Mac that has never run low-talker also runs Gatekeeper's first check of the notarized bundle. On an Apple M5 Max running macOS Tahoe that had never run low-talker, the notarized release (v0.1.0-alpha.2) was reported to launch with no Gatekeeper prompt (how that copy reached the Mac, and so whether it carried a quarantine, is not recorded) and was ready 2 min 4 s after launch, the network on — quicker than the M2 Max here, on a newer Neural Engine. With the network off, on a Mac that had never looked up the release's notarization ticket, the image mounted with no prompt and the app launched out of it after macOS's usual first-open confirmation ("Signing for release" below).

CI has no model cache, so the tests cover the mapping from WhisperKit's results onto `Transcript` with hand-built results and the manifest logic on scratch files; the real engine is exercised only by the app and its bench.

### The latency harness

The bench runs in the app. **Benchmark…** in the menu opens a window with a control for each option below: a fixtures folder and a model store, each chosen with **Choose…**, the models that store holds, the deliveries, the servings, the runs, and the vocabulary as comma-separated terms. The store defaults to the one the app carries; **Use Carried** goes back to it. **Run** fills the window's table row by row, **Cancel** stops the run at its next hold, and **Copy Table** copies the table as tab-separated text. The app is sandboxed, so it reads a folder only once it has been chosen in the window's open panel, which remembers it as a security-scoped bookmark; `~/Library/Application Support/low-talker/hub` and a checkout's `bench/` are read that way, never by path. A run starts only while no dictation is being heard, and holds the engine until it ends: a press made meanwhile is refused, and the menu and the press's failure line both say a benchmark is running, while a served request waits for the run as it waits for a press.

Each option is named here by the flag `LowTalker --bench` takes for it (below). The bench walks the fixtures folder and loads every `<name>.wav` beside a `<name>.txt` holding the reference text. A fixture is named by its path under the directory without the extension, so `say/greeting`. A wav without its txt, a txt without its wav, a reference with no words, or a directory with no fixtures at all is an error, not a skipped file, so the set cannot quietly shrink. `--model` may be repeated and defaults to the app's default model. `--delivery` is how a hold's audio reaches the engine, `batch` (the whole clip at key-up) or `streamed` (0.1 s at a time, a size the bench fixes so its runs compare with one another; the microphone's own buffers are the device's to size, around 10 ms on the built-in one); it may be repeated and defaults to both. `--runs` (default 3) is how many times each fixture is held per delivery; the first hold after a load is reported apart from the median of all runs, because after the warm load at launch the first dictation of a session pays it. `--vocabulary`, repeatable, is told to the engine on every hold, so a run with it against a run without shows what a vocabulary does to every fixture, the ones that say its terms and the ones that do not. `--models-dir` picks the model store. `--serving` is what else asks the engine during each hold: `idle` (the default) or `served`, where a 40 s upload made of the fixtures end to end, from the first again once they run out, is decoding when the key goes down, a second arrives halfway through the hold, and a stream runs from before key-down to key-up, all through the served side of the same engine; it may be repeated. Every hold holds the engine as a press in the app does, so a served row's latency beside its idle row is what serving costs dictation. The `served_cancelled` and `served_deferred` columns count the served decodes the holds cancelled (each run again) and made wait, and `served_changed` counts uploads that read otherwise than the same upload heard before any hold.

Each hold is simulated in real time: a chunk reaches the engine at the moment its audio would have been captured, the key comes up with the last chunk, and the clock runs from there until the transcript is back. The table is tab-separated, with a header row and one row per model, fixture, delivery, and serving, flushed as each row lands. The columns are `model`, `fixture`, `delivery`, `serving`, `audio_s` (the clip's length), `load_s` (the model load, once per model), `first_s` and `median_s` (key-up to transcript on the first hold and the median over all runs), `partial_s` (the median from the hold beginning to the first text the engine showed: the first partial, or the transcript when there was none), `wer`, its split into `substituted`, `dropped`, and `added`, `reference_words`, and the three `served_` counts. Durations are seconds to three places. From a terminal, the table goes to stdout and stderr narrates the load phases and prints what the engine heard for every fixture with its error count, which is how a nonzero word error rate gets explained.

Each event of a run is one line in the unified log under the `bench` category, the start with its options, each model's load, each row as `name=value` fields, and how it ended:

    /usr/bin/log show --info --last 1h --predicate 'subsystem == "ai.promptctl.low-talker" AND category == "bench"'

The app's own binary runs it from a terminal, with the flags above, and reads the folders the window remembered:

    /Applications/LowTalker.app/Contents/MacOS/LowTalker --bench ~/code/low-talker/bench --runs 5

That process stops before the app starts: it shows no menu-bar item, registers no hotkey and talks to no input method. A menu-bar app running beside it knows nothing of the run, so its presses and served requests are heard during it and measured against it. It exits 1 when the run fails, a fixture folder that will not read included. A folder the window never chose is refused by name, with where to choose it. `--models-dir` names a store chosen in the window, and the carried store is the default.

Streamed, the engine decodes during the hold. Whisper reads a whole window at a time, so streaming is re-reading: every pass decodes from a few confirmed words back to the speech so far, and a word two passes in a row agree on is confirmed once it ended at least a second before the later pass's end (the local-agreement rule of whisper_streaming, Macháček et al. 2023; the second is WhisperKit's `windowClipTime`, under which it decodes no window). The confirmed words a pass starts from are forced as its first tokens, decoded over the audio that contains them, and their re-reading is dropped; prompting them as earlier text instead made Whisper read them a second time out of the audio that followed ("Hello Hello world"). They are forced without their final punctuation: told "and drinking blood." and then hearing a pause, Whisper closed the transcript there and lost the seven words after the pause, while told "and drinking blood" it read the period back and went on. A pass runs whenever the engine is free and new speech has arrived, where speech is a buffer whose peak stands within 24 dB (a factor of 16) of the loudest buffer so far, judged once as the buffer arrives, plus 0.3 s of hangover for a word's soft tail. Only the loudest buffer of the utterance must reach 0.01 (-40 dBFS; room noise on the built-in microphone peaks at -49 to -54), and an utterance whose loudest never reaches it is refused with that peak rather than decoded (Whisper read over silence hallucinates), and the transcription server answers it as nothing said. Trailing quiet never starts a pass, so when the speaker stops before releasing the key, the pass in flight at key-up is the last one and key-up waits only for it to finish. During the hold the first pass waits for a second of speech, but the end of the utterance is worth a pass over whatever no pass has heard, however short: WhisperKit decodes no window that spans a second or less from its start, so a pass over less than that, the whole of a tap-to-toggle "yes", is run out to one sample past that floor with silence, the same silence the encoder pads every window with. Audio already past the floor is handed over untouched, so the guard still refuses a trailing sliver of a long clip as it did. `say/yes`, 0.48 s of speech, is heard on both deliveries where before it came back as nothing; its row in the table below is from a later run of the same command, and is one pass over the whole clip either way, so both deliveries land at 0.63 s and its first text is the transcript.

Where a pass's time goes, from a probe of one pass over the 4.4 s clip: the log-mel spectrogram 0.04 s, the encoder 0.39 s, twenty decoder steps 0.23 s, so 12 ms a token. The encoder always sees a window padded to 30 s, so 0.39 s is the floor of any pass that hears new audio however short the tail is, and a forced prefix token costs a decoder step like a decoded one. A pass over a few words of tail is therefore about 0.5 s, not much under a batch decode of a short clip, and streaming does not win by making the key-up pass small. It wins when the pass in flight at key-up is the last one: key-up then waits only for that pass to finish, anywhere from nothing to one pass, which is the 0.29 to 0.64 s medians on five of the six recordings. When speech runs right up to key-up, key-up waits for the pass in flight and then one more, so the `say` clips land between 0.04 s ahead of batch and 0.25 s behind it. The first text lands 1.30 to 1.35 s into the hold on the longer clips: the first pass starts once 0.7 s of speech plus the hangover has arrived and takes about 0.5 s. It is 1.52 s on the two-second `say` clips, and 2.00 s on librispeech/2803, whose first pass, over 0.3 s of speech after half a second of leading quiet, takes 1.0 to 1.2 s where the same cut of another recording takes 0.6 s. Under 300 ms from key-up needs the encoder off the key-up path, a smaller or a genuinely streaming encoder, which is the case the Parakeet engine has to make. The other hazard in this run was WhisperKit's temperature ladder, since switched off (see below): its retries hit two of librispeech/6313's three streamed holds, the first at 5.29 s, and are the whole of that row's 3.69 s median.

The vocabulary check is two full runs of the bench under the same conditions, one bare and one with `--vocabulary Brynleigh --vocabulary Fryslie --vocabulary Jaxxon`. The vocabulary reaches Whisper as its initial prompt, the text of a segment before the utterance: the terms space-joined, each with the leading space a spoken word carries, so " Brynleigh Fryslie Jaxxon". A comma-separated list read its commas back into the transcript. WhisperKit keeps at most 111 prompt tokens, and the transcriber refuses a longer vocabulary rather than let it lose its first terms silently. `say/names` reads "Ask Brynleigh Fryslie to review the pull request before Jaxxon merges it." Bare, the engine heard "Ask Brynley Frisley to review the pull request before Jackson merges it." batch, 3 of 12 words wrong, and "Ask Brian Lay Frisley ... Jackson" streamed, 4 wrong. Told the three names, it made 0 errors on both deliveries. The other twelve fixtures heard the same words with the vocabulary as without: the only error in either run is the shared "pushed to talk" on `say/jargon`, and none of the three names appeared in a fixture that does not say them.

The cost is decoder steps. Brynleigh, Fryslie, and Jaxxon are 10 tokens, plus the start-of-previous token, so 11 decoder steps a pass, about 0.13 s at 12 ms a token. Batch key-up to transcript rose 0.07 to 0.17 s per fixture (`say/meeting-request` 0.67 s to 0.78 s, `say/names` 0.71 s to 0.88 s). Streamed medians rose 0.1 to 0.4 s on most fixtures (`say/greeting` 0.59 s to 0.99 s, `say/meeting-request` 0.90 s to 1.16 s, `say/status-update` 0.78 s to 1.12 s), because every pass pays the prompt and key-up sometimes waits for two. One streamed row in each run was a temperature-ladder outlier, librispeech/6313 at 4.15 s bare and librispeech/777 at 2.16 s with the vocabulary, the hazard the next paragraph turns off. First text landed 1.43 to 1.46 s into the hold on most clips against 1.30 to 1.35 s bare, and later on four whose first pass retried (librispeech/251 4.70 s, librispeech/777 3.07 s, `say/status-update` 4.71 s, `say/jargon` 2.44 s). Getting these numbers meant working around a WhisperKit 1.1.0 bug: with a prompt set it writes each decoder step's alignment row at the step's index in the whole prefilled sequence, prompt included, but reads word timings by the token's index from the start-of-transcript token, so every word was read 11 rows early, the 2 s clips came back with no words, and streamed passes dropped tail words with latency up to 10.7 s. `SpeechAlignedSegmentSeeker` in LowTalkerCore hands WhisperKit's own seeker the rows from the start of the transcript on. Upstream has no fix as of September 2026. The same seeker also hands it only the columns the pass's audio fills, as Whisper's reference aligner does. WhisperKit aligns over the whole 30 s window, and on 3 s of noise it timed a word at 29.1 s.

The temperature ladder is off: one decode a pass, at temperature zero. By default WhisperKit re-decodes a window at rising temperatures, up to five more times, when the reading looks repetitive (compression ratio over 2.4) or under-confident (mean log probability under -1.0), and a first token under -1.5 aborts a decode at once so the next rung starts sooner; each rung is a full decoder loop over the same encoder output. A probe of every pass in a five-hold bench found the ladder climbed on nothing but mid-hold passes cut into a word. The first pass over librispeech/2803, 0.6 s of "The jailer" after half a second of quiet, took three to five rungs on every hold, 1.0 to 1.2 s, to read "the gym", and at the fifth rung nothing at all; the pass over librispeech/6313 that ends inside "indignation" took two to five rungs, 1.5 to 4.4 s against 0.6 s for a plain pass, and at the top rung read "Lumpy, filled with, filled with, Filled with ignatation that, Anyone should". Not one of the seventy batch holds, each a single pass over a whole utterance, climbed it. So `temperatureFallbackCount` is 0 and `firstTokenLogProbThreshold` is nil, the abort having nothing to abort for. Five holds per fixture and delivery, before and after, on the fourteen fixtures: the word error rate is the same on all 28 rows and the transcripts differ by one comma; the longest pass is 1.37 s where it was 4.40 s; librispeech/6313 streamed is 0.37 s first and 0.90 s median where it was 1.27 s and 1.82 s; and librispeech/2803's first text lands 1.3 s into the hold where it was 2.0 s, its first pass 0.5 s instead of 1.0 to 1.2. What the ladder was catching shows once: at temperature zero that 6313 pass reads "Lumpy, filled with, filled with, filled with", a loop, in 0.9 to 1.4 s, and the next pass 0.7 s later reads the sentence, so the loop is on screen as a partial for under a second and never in a transcript. A loop on a final pass, the one no later pass corrects, would be delivered as read, and that is the accepted trade: on the looping 6313 pass the ladder's rungs read back a truncated "Lumpy, filled with", the stutter quoted above, or on librispeech/2803 nothing at all, so its answer to a loop was a shorter or empty reading at one full decode per rung, and in dictation a visible loop is redone where a clause silently gone is not noticed. Streamed key-up on the recordings that end in room quiet moved both ways between the two runs (librispeech/2277 0.27 s to 0.69 s, 3536 0.32 s to 0.84 s) with every pass identical in count, cut, and duration: on those the number is whether the last pass happened to start just before key-up or just after, and it is the harness's phase, not the ladder's. For the next probe: `timings.totalDecodingFallbacks` is the index of the last rung that fell, so a pass that retried exactly once reports 0.

The speech gate follows the utterance: a buffer is speech when its peak stands within 24 dB of the loudest buffer so far, and only the loudest must clear an audible floor of -40 dBFS, where before every buffer had to reach -34 dBFS on its own. A ratio does not move when the level does, so a soft speaker or a low-gain microphone is cut into the same speech and quiet as a loud one, and a fixed level is not: streamed over the bench fixtures attenuated by 20 dB, the old gate returned librispeech/2277, 3536, and 777 with key-up 0.000 s, no final pass having run, because their soft trailing buffers fell under -34 and the words after the last loud buffer plus the hangover were never decoded, 7 words lost in all ("future"; "his minister's domestic arrangements"; "like that"). A gate relative to the utterance's own noise floor was the other candidate, and it fails because the `say` fixtures have no quiet in them: say/meeting-request's softest 0.1 s buffer is -13.8 dBFS and its loudest -2 to -4, so any rule that accepts it and refuses a silent room (-47 to -54 dBFS in every buffer, also no contrast) must contain an absolute level, and the absolute sits on the one question only level can answer, whether there is a speaker at all, asked once of the loudest buffer; so `Utterance.audible` is 0.01 and `Utterance.dynamicRange` is 16. The 24 dB came from simulating the rule buffer by buffer over all fourteen fixtures against the old gate, for ranges of 20 to 32 dB: at 24 dB, 18 buffer judgements out of about 800 differ, all mid-utterance, and the last speech buffer moves back by one on three `say` fixtures whose final buffer is already inside the 0.3 s hangover, so the last pass covers the same audio; at 20 dB six fixtures moved; at 28 dB and above speech ends moved later on librispeech/777 and 251. The softest LibriSpeech speech under the old gate sat 19 to 27 dB under its utterance's loudest. With the new gate, five holds on both deliveries, the 20 dB attenuated set scores the same word error rate as the original on 26 of 28 rows, every LibriSpeech fixture at 0 errors both ways; the two rows that differ are say/names, whose unaided names flip between runs at full level too. At 30 dB down, the loudest buffer at -42.8 dBFS, the utterance is refused. A silent hold costs what it did: 2.9 s of steady room noise at -47 to -53 dBFS is refused with peak 0.0043 before any decode, and on the original fourteen fixtures the word error rate is identical on all 28 rows against the previous run. The trade is in what a peak knows, which is level: a click at or above -40 dBFS is a speaker, an exposure the -34 gate had too (room clicks and typing measured -25 to -40 dBFS a buffer, so it is not new in kind); and a soft speaker whose room noise sits within 24 dB of their loudest gets passes over trailing quiet. The range cuts the other way too: the loudest clip never falls, so a transient louder than any word, a door or a dropped object, sets the bar for every clip after it, and speech more than 24 dB under it is trimmed as quiet. A transient at -10 dBFS puts speech at the old gate's -34 out of range; one at full scale puts speech under -24 dBFS out of range. Speech before the transient stays speech and the pass over the speech through it still runs, so the exposure is a soft speaker, loudest word under -24 dBFS, losing the words after a near-full-scale slam that the old gate would have heard; the fixtures at full level peak at -2 to -12, inside the range of anything.

Word error rate is (substitutions + deletions + insertions) / reference words, by minimum edit distance over words, with reference and hypothesis normalized the same way first: lowercased, a word being a run of letters, digits, and apostrophes, so hyphens and punctuation separate. An apostrophe at a word's edge is a quotation mark and is dropped; inside a word it is a contraction and stays.

The fixtures live in `bench/`. `bench/say/` holds eight utterances written as `.txt` files and rendered to 16 kHz mono wav with the Mac's `say` command (voice Samantha) by `scripts/make-bench-fixtures`; `say/names` is the one with names Whisper cannot spell unaided, for the vocabulary check above, and `say/yes` is the one under a second, which keeps sub-second speech heard. There the text is the source and the wav is derived, but the wav is committed because a synthesizer voice changes with the OS and the numbers are only comparable over the same audio. `bench/librispeech/` holds six human utterances from the LibriSpeech corpus (dev-clean split), one per speaker, with their transcripts, converted to 16 kHz mono wav; these are recordings, so the wav is the source and the txt is its transcript. LibriSpeech is CC BY 4.0 (Panayotov, Chen, Povey, Khudanpur, 2015). Synthesized speech turned out too clean to rank the models on accuracy: small.en and base.en score exactly as the large models do on it, and only the distilled pair adds an error; the human recordings are what separate them.

## Microphone permission

The app asks for the microphone on its own behalf, from the microphone step of its guided setup ("The guided setup" below), and never at launch. macOS posts no notification when the switch is flipped in System Settings, so a change is only seen by reading the status again, which the menu does each time it opens and the setup each time it comes to the front.

To see the app's microphone step and its prompt again, forget the app's decision and relaunch:

    tccutil reset Microphone ai.promptctl.low-talker

## The config file

The app reads its file, `.config/low-talker/config.toml` inside its container, `~/Library/Containers/ai.promptctl.low-talker/Data`, at launch, and again every time it is saved, so an edit takes effect with no relaunch. No file at all is not an error: the app runs on the defaults, dictation on Right Option with the default model, and deleting the file goes back to them. A file that exists but cannot be read, or cannot be understood, is an error and is never quietly replaced by the defaults, since a config the user wrote and the app silently ignored is worse than one it refuses. A save refused that way leaves the app on the config it was already running, and the menu's Config line says why until a save it can read replaces it; a file refused at launch leaves the hotkey off until then. A press open while a mode or the microphone's resting mode changes is not cut short: a hold ends at the release of the chord that began it, a tap left listening ends at the next press of that chord or the new one, the press is heard expecting its mode's vocabulary as it stood when the chord went down, and the microphone takes up its new resting mode at that key-up. A changed `[serve]` table restarts a listening server on the new binding.

The file names a `model`, a model folder name such as `base.en`, an optional `[microphone]` table saying what the device does between presses, an optional `[serve]` table saying where the transcription server listens, and an array of `[[modes]]` tables. Each mode takes a `name`, an optional `chord`, and an optional `vocabulary` of terms, which every press of that mode's chord hands the engine before its first word.

    model = "base.en"

    [[modes]]
    name = "dictation"
    chord = { modifiers = ["rightOption"] }

    [[modes]]
    name = "notes"
    chord = { modifiers = ["leftCommand", "leftShift"] }
    vocabulary = ["Kubernetes", "Anthropic"]

A chord is modifier keys, at least one. The app is told only when a modifier key moves, so a key besides them could never complete a chord, and a `key` is refused as a word the schema has no place for. It is the chord the app listens for and the menu names. A mode with no `chord` listens for the default, Right Option, so only one mode may leave it out: two would listen for one chord, and the file is refused naming the second. A key the schema has no place for is refused rather than ignored, so a typo is told rather than silently doing nothing. A chord written under a hotkey source's name, `chord = { inputMethod = { … } }`, the way a config named one per source before the input method was the only way the chord is heard, is refused as `modes[0].chord.modifiers is missing`. So is a mode's `routes`, which configs carried while the app had more to do with a transcript than insert it: `nothing in a config is called "modes[0].routes"`, and deleting the key leaves the mode dictating as it did.

The `[microphone]` table is optional, and the file above leaves it out: with no table at all the microphone is `shut`, opened when the hotkey goes down and closed when it comes up, so the indicator in the menu bar is a record of what you dictated rather than of how long the app has been running. `at_rest = "open"` takes the trade the other way and holds the microphone from launch to quit. What that buys is the look-back, the 0.3 s of already-captured audio a press reaches back over, so a key pressed a syllable into a word still catches that word; what it costs is a lit indicator and a privacy report saying low-talker is listening on a Mac nobody has spoken to. There is no wake word yet, so `at_rest` is the only thing that holds the microphone open while nobody is dictating: it is in the file or it does not happen. The key is required once the heading is there. A `[microphone]` with nothing under it is refused as `microphone.at_rest is missing`, since a heading somebody wrote on purpose cannot be read as the default they were already getting, and any other word is refused with that word quoted back, as `microphone.at_rest: "sometimes" is not something the microphone does at rest`.

The `[serve]` table is optional too, and without an `interface` the server listens on loopback, where it answers every caller whatever token it sends, since local clients send placeholder keys. `interface = "192.168.1.20"` (one interface's numeric IPv4 or IPv6 address) listens there instead, and then `token` is required: every request and every Realtime upgrade must carry `Authorization: Bearer <token>`, the header both Pipecat services send as their `api_key`. A caller without it gets a 401 in OpenAI's error shape, or on a socket an `invalid_api_key` error event and close code 3000. An interface with no token is refused naming `serve.token`, a token with no interface is refused because loopback would ignore it, and an address that takes in loopback is refused: loopback itself, `0.0.0.0` or `::`, which listen on every interface, or loopback written as IPv6. So is a `[serve]` heading with nothing under it. The token may hold only letters, digits and `-._~+/`, then any `=` padding. TLS is not the app's: put a proxy such as Tailscale Serve in front of it.

The menu names a fault, and how it names it depends on how far reading got. A file that is not TOML at all names the line reading stopped on. Anything that is TOML but wrong is named by its path in the document instead, as `modes[1].vocabulary[0]: vocabulary term "..." has no word in it` or `modes[1].name is missing`, and carries no line number: decoding reports the path it was at, and the TOML library exposes source positions only for a parse error, not for a document that parsed. The path counts `[[modes]]` entries from zero, the way the file writes them, so the entry it names is one the reader can count to.

## The input method

LowTalker puts what you dictate at the cursor through its own macOS input method. The input method is a small second bundle that the installer package puts in `/Library/Input Methods`; the app registers it and - once you have switched it on in setup, the one step macOS asks you about - selects it at every launch and keeps it selected. The app never copies or replaces it. Its controller passes every key through untouched, so typing is unchanged while it is the selected source. Nothing is posted as a key, nothing asks for an administrator, and the pasteboard is never touched.

The app hears the chord itself. A global and a local event monitor of `flagsChanged` hand it every change of the modifier keys, in any app, and macOS asks for no grant for them, where a monitor of typed keys would need Input Monitoring. So a press is heard whichever input source is selected and while an app holds Secure Event Input (measured on studious and u2, 2026-10-20). Its words are typed only while LowTalker is the selected input source and no app holds Secure Event Input. Otherwise the insert is refused by name and the words are held, and the menu reads both each time it opens and names whichever stands under its Hotkey line, as `Not typed now: LowTalker is not the selected input source`. A release no event tells is still heard, since the app reads the modifier keys itself while one is held. The input method tells the app each cursor it is given focus in, over a port the app hosts (`ai.promptctl.low-talker.hotkey`) that hears only its own input method. Hosting that port is also what keeps a second copy of the app from listening.

When the input method's process ends, macOS does not start it again, so the app does. While the hotkey is up, the app opens the input method through LaunchServices without taking the front. It watches the process, and when the process ends it opens it again, never sooner than 10 seconds after the last open, as launchd throttles its own daemons. Until one is running again, the Hotkey line says the input method ended and is being started again, or why it could not be started. The app in front gives the new process its client with no change of focus (measured on studious, 2026-10-18).

Hold the chord while you speak, or tap it to start and again to stop: a press released within 250 ms is a tap, and listening stays on until the chord is pressed again. A chord is modifier keys alone, and pressed with another modifier already held it is a different chord. A chord held while another key is typed was that key's modifier, Option for a special character, so the press ends as the chord comes up, however long it was down: nothing more of it is inserted, and no failure is shown. No typed key reaches the app, so with each change it reads when the session last saw one, counted only if it came before that change's own event. A key typed in the moment after the release hides any typed under the chord, and that press is judged by its length.

Fn, the Globe key, can be a chord, written `"function"`. Fn is held only while the Fn key itself is down. macOS also marks the arrow, Home, End, Page Up, Page Down and Forward Delete keys as Fn, and those do not count. Set System Settings › Keyboard › "Press 🌐 key to" to Do Nothing, or macOS runs its own action on every press as well. That action might start Dictation, show Emoji & Symbols, or change the input source away from LowTalker. While a chord holds Fn and that setting is anything else, the menu says so under its Hotkey line and names the setting.

An installation from before the input method was the only way still holds its old answers in its defaults, under `inputMethod` and `hotkeySource`. Nothing reads them now, so it comes up on the input method with no question asked. Such an installation also still holds the keyboard helper it registered as a background item. v0.1.0-alpha.5 unregisters it at launch. A build under App Sandbox is not permitted to (`SMAppService` answers `Operation not permitted`), so an installation that goes straight from alpha.4 or earlier to a sandboxed build keeps a job whose program is gone; `sudo launchctl bootout system/ai.promptctl.low-talker.keyboardd` (and `com.lowtalker.keyboardd`, `.dev` for what was the development copy) drops it.

## Dictation

The app runs the loop: hold the chord, speak, release, and what was said is inserted at the cursor. Key-down marks where the utterance begins on the audio ring and reads which app is in front, and the engine hears the press as it is captured. Words land as they are confirmed: each time a pass confirms words past those already inserted, the new ones are inserted while the key is still down, and key-up inserts the rest of the transcript, so no word is inserted twice. An insert the input method refuses during a press holds its words, and the next insert carries them. A press that lapses, has its chord used as a typed key's modifier, or loses audio inserts nothing more, but its decode still hears it to the end of its audio, across any gap, and what it heard past the inserts is held. Either way the words already inserted stay, and the report says how many landed and how many are held. Sessions are heard and inserted on one serial queue, so two presses in quick succession insert in the order they were spoken however long the engine takes on either. Each session is one line in the unified log under the `dictation` category: how many words were heard, how long after key-up and how much of that the key-up spent reaching the app, how many inserts landed while the key was down and how long after key-down the first did, and which app's cursor took them.

The loop is its own module, `Sources/Dictation`, and the microphone, engine, executor, frontmost-app reader and the reporter that hears the outcome are values it is given, so the whole of it runs under `swift test` against a fake of each.

## Insert

Inserting needs no grant at all. The app asks the input method to put text at the cursor through the text input system, the way a Japanese or Chinese input method commits a candidate, so nothing is posted as a key and the pasteboard is never touched. The LowTalker input source has to be selected for it; the input method process launches on demand.

The input method takes words only from the app. The name the app sends to can be computed by any process, so every request is checked against the sender's code signature before its words are read. The sender has to be the app's bundle identifier, signed by the certificate that signed the input method, under the hardened runtime. The signature is the one the kernel holds for the running process, because the input method's sandbox cannot read the sender's executable from disk. Anything else is refused with `senderIsNotThisInstallationsApp`, and the input method's log names the pid it turned away, who that process is, and who it needed to be. The check runs the other way too. A name anyone can compute is one anyone can hold first, so before sending any words the app asks whoever holds the name who it is. If the answer is not from its own input method, signed as the app is, the app sends nothing. There is no command-line `insert` for the same reason. A command any process can run would let any process type.

When an insert fails, the app reports why by name, because either way the words are not at the cursor. A refusal says why: no text field has focus (no client has focus, the client in front gives no document access, as a window with no field focused does, or its caret is on no screen, as the Finder's type-select buffer's is), the cursor is in an app that is not in front, LowTalker is not the selected input source, an app has secure keyboard entry on, or the sender is not the app. A transport failure says which one it was, because a request the input method never took means the words did not land, while an answer that never came back means they may have.

What `inserted` claims is that the client belonging to the app in front answered that it gives document access, with its caret on a screen or reported nowhere, and accepted the commit, not that a person saw the words - the text input system offers no delivery report. The Finder's desktop and file lists answer that they give document access too, from a type-select buffer in no window, and the caret check is what refuses them: that buffer's caret line sits below the bottom edge of the main display.

Verified on this Mac with the development copy, 2026-09-24: a held chord over the fixture `say/greeting`, played to the microphone, landed the words at the cursor in TextEdit, Safari, Chrome and iTerm2, confirmed in the input method's log, with TextEdit reading back "Hello world, this is Low Talker." — and in VS Code. Those are the apps the slice's checkpoint covered, chosen because they span the cases the input method has to reach: a native text view, a WebKit browser, a Chromium browser, an Electron editor, and a terminal. An app left running through an earlier build's input-method restarts is shut out by macOS's `imklaunchagent` until it relaunches or the user logs out, so each app is relaunched before the run, or its refusal measures that history rather than this build. Secure Keyboard Entry, which iTerm2 can turn on, is its own named refusal (above); toggling it is left to the operator.

## What is left to set up

The menu lists everything that must hold before low-talker can hear and type, read off this Mac each time it opens, with the step for whatever is missing indented under it:

    Microphone: allowed
    Input method: switched on

Every row is `Name: what was read`. Every row is shown every time, met or not, since a list that showed only what was wrong leaves a reader unable to tell "checked and fine" from "never checked". A fact that could not be read is a row of its own reading `could not be read`, with the reason as its step, and it never counts as met, so a reading nobody managed to take can never come out as ready.

The menu and the guided setup read one list, assembled in `OnboardingProbe.readiness` and nowhere else. The menu holds no state either. It is emptied and rebuilt from a fresh reading every time it is about to be shown, in `NSMenuDelegate.menuNeedsUpdate`, rather than cached, because a cached reading is stale exactly when it matters: right after the user has given the grant the menu was telling them to give.

### The guided setup

The app launches without raising any system dialog: no Microphone or input method prompt. Launch reads every grant, which asks nothing, and brings dictation up as far as what is already granted allows. What is missing is asked for from Set Up LowTalker… in the menu, which opens on its own at a launch that finds something missing, since nothing can be dictated until both steps are met. The menu item says how many steps are left.

The setup is a walk over the same list the menu shows, one requirement per page. Each page says why the app asks, what the grant lets you do, and what still works if you skip it, before the button that makes macOS ask. Pressing that button raises one system dialog, naming the app. Skip for Now moves on and leaves the app running; skipped steps wait on the last page, each with what skipping it costs and a button back to it. The page is redrawn from a fresh reading whenever the window comes back to the front, so a switch turned on in System Settings clears its step there without a relaunch. When a reading after a request, on coming back to the front, or on opening the menu finds a grant the previous reading of the same setup did not, dictation comes up behind it. The microphone's dialog is shown once per app, so once its step has been asked in a walk and is still unmet, its button becomes Open System Settings and the page says why. The input method is the exception: macOS shows its Allow dialog again on the next press (measured on studious, 2026-09-27), so its button stays and the page never sends the person to System Settings with "asks only once".

| Step | What the button does |
|---|---|
| Microphone | asks for the microphone (`AVCaptureDevice.requestAccess`) |
| Input method | switches the input method on (`TISEnableInputSource`), which macOS asks about in a dialog naming the app; it asks again after a No |

Those are the only places the app calls anything that can put a dialog on screen. The input method is copied and registered at launch but never switched on there.

So the microphone's row reads one of four things:

- `allowed` means the app can hear.
- `not asked yet` means macOS has never been asked, and the setup's Allow button is what asks.
- `turned off` means the person declined or switched it off since, and only System Settings > Privacy & Security > Microphone turns it back on.
- `restricted by policy` means whoever manages this Mac has forbidden it.

So the input method's row reads one of two things:

- `switched on` means macOS lists the input method and its one mode as on, and the app selects the mode itself.
- `switched off` means either is not on yet, whether or not it has been copied and registered: never allowed, or removed under Keyboard > Input Sources, which switches the mode off.

The app logs every reading it takes, so an agent can read back what the menu is showing without a screen:

    /usr/bin/log show --predicate 'subsystem == "ai.promptctl.low-talker"' --last 5m --style compact

The category is `engine`. Each open writes `onboarding: ready` or `onboarding: not ready`, then one `onboarding: <Name>: <what was read>` per requirement, then `hotkey: words held, not typed, because [...]` with whatever the menu's "Not typed now" lines name. `log` is spelled with its absolute path because zsh has a builtin by that name.

## What a release ships, and under what license

`make sbom` writes `sbom/lowtalker.cdx.json`, a CycloneDX 1.6 bill of what reaches a user's Mac: every package Package.resolved pins, the third-party code vendored inside those packages, and the model the app loads, as its weights and its tokenizer. Identity, URL, version and revision are read off the resolved build and never typed: Package.resolved for the packages, the checkouts under `.build` for the vendored code (swift-transformers writes its version and commit into the header of each file argmax-oss-swift carries under `Sources/ArgmaxCore/External`; toml++ has its version in three macros of the one header TOMLKit carries), and `model-tool default` for which model. `sbom/rules.json` holds only what none of those can say: the license each component is under, the file in the checkout that license was read from (that file's digest goes into the SBOM, so a changed file is a changed reading), which packages carry code no manifest declares, and which Hugging Face repos the default model's two parts come from. The repos state their own licenses, and they differ: `argmaxinc/whisperkit-coreml` is MIT and the tokenizer's repo `openai/whisper-large-v3` is Apache-2.0.

The two repos are the one thing a clean checkout cannot check, because WhisperKit picks the tokenizer's repo off the weights' config once they are downloaded. So wherever this Mac's store holds the model, `make sbom` holds the rules to the folders that install wrote, and a rule naming a repo the install did not fetch from stops the run; the store changes nothing in the file. A package pinned with no rule, a rule for a package no longer pinned, a license file not where the rule says, a vendored version the files no longer match, or a default model the rules do not know each stop the run and name the component, because a row missing from an SBOM is believed. The file carries no timestamp and no serial number, so the same checkout writes the same bytes twice, and `make test` regenerates it and fails if the committed file is not what the build writes, so a bumped dependency cannot leave a stale bill behind. The app build resolves only what Package.resolved pins, so the bill names the versions the bundle links, and `scripts/sign-release` runs `make check-sbom` against the store it is about to bundle, holding the model rules to what the release carries. Measured on 2026-09-28 from a fresh worktree of master: five components (three packages, two model parts) and two vendored, a second run byte-identical, a fourth pin added to Package.resolved stopped the run with `Package.resolved pins swift-log, and sbom/rules.json has no entry for it`, and a tokenizer rule changed to `openai/whisper-large-v2` stopped it against this Mac's store, naming `openai/whisper-large-v3` as what the install came from.

`make test` then runs `scripts/check-licenses` over the committed file, so every pull request is gated on it in CI, and `scripts/sign-release` runs it before building what it ships. It fails on any component, vendored ones included, whose licenses are not all SPDX ids in the accepted set (`ACCEPTED` in `scripts/check-licenses`: the permissive licenses and public-domain equivalents), and on any component whose license was not identified, naming each one with its version and what it is under. When it fires, the response is already decided: drop the dependency, replace it with a permissively licensed equivalent, or reimplement its behavior clean-room from a black-box specification written by someone who has not read its source. Shipping it while deciding is not an option, because the obligation attaches on distribution.

## What the app sends

Nothing. The app links no code of ours that reaches the network; the only code in it that can is WhisperKit and the Hugging Face hub client vendored in argmax-oss-swift. `scripts/wire-check <app bundle> <input method bundle>` watches that on the wire: it relaunches the app and its input method under `log stream`, waits for one dictation to reach the input method, and passes only if neither process logged any network work outside a short allow list of path-evaluation lines measured on an idle launch. It repeats a request of its own with `nscurl` until the capture shows it, since a blind stream would also come back empty. The hub client does start an `NWPathMonitor` as the tokenizer loads (`HubApi.swift`, `NetworkMonitor`), which asks whether a route exists and opens nothing; the check counts those and passes them.

`silentOnTheWireAt` in `sbom/rules.json` is the argmax-oss-swift revision the check last passed at, and `make sbom` stops on any other, so a bump fails `make test` until someone re-runs the check on a build of it and records the new revision. Measured on 2026-09-29 at 1.1.0 (`1e2a163`) against the installed development build.

## The development signing identity

`make app` and `make test` run `make signing-identity` before they sign, so a fresh clone needs no setup step.

### Why a certificate

macOS keys the Microphone grant to the app's code signature, its "designated requirement". For an ad-hoc-signed build that requirement is the hash of the specific binary, so every rebuild is a new app as far as macOS is concerned and the grant is gone. For a certificate-signed build the requirement names the certificate instead, and it survives rebuilds.

### What the command does

`make signing-identity` leaves a self-signed code-signing certificate named `LowTalker Dev` usable by `codesign` with nobody at the screen. On a Mac without one it creates it, valid for ten years. It keeps it in a keychain of its own, `lowtalker-dev.keychain`, whose password `scripts/make-signing-identity` holds, and on every run it unlocks that keychain, turns off its auto-lock, adds it to the user's keychain search list, and sets the key's partition list. A key in the login keychain has an empty partition list, so its first signature waits on a "codesign wants to sign using key" dialog: the build hangs rather than fails, and no build can supply the login password that would clear it. Every run ends by signing a scratch file under a 20-second deadline, so an identity `codesign` cannot use stops the build with a message instead of hanging it. It sets no trust settings on purpose; `codesign` does not need them. It refuses to run when two identities share the name, since that makes every build ambiguous.

Because the keychain's password is in the repo, anything running as you can sign as the development build and so meet the requirement its permission grants are keyed to. Release builds sign with Developer ID and are not affected.

A `LowTalker Dev` made before 2026-10-18 lives in the login keychain. The command leaves it there. It signs without a dialog only where someone once answered Always Allow; elsewhere the trial signature fails and says how to replace it.

The name lives in one place: `project.yml` sets `CODE_SIGN_IDENTITY` to `LowTalker Dev`, and the Makefile reads it from there.

To confirm a build is signed with it:

    codesign -dvvv --requirements - "DerivedData/Build/Products/Release/LowTalker.app"

The `designated =>` line should name `certificate leaf = H"..."`, which is stable across builds. An ad-hoc build shows `cdhash H"..."` instead, and that hash changes every build.

### Hardened Runtime and entitlements

The app, everything embedded in it, and the input method bundle it is packaged with are built with Hardened Runtime, which notarization requires: `project.yml` sets `ENABLE_HARDENED_RUNTIME`. `codesign -dv` on the app or on its input method bundle in `/Library/Input Methods` shows `flags=0x10000(runtime)`.

The runtime holds a program to a set of restrictions, and each exception is an entitlement. Each app's are declared under `entitlements` in `project.yml`; xcodegen writes the plist from there into `App/Generated/`, which is ignored.

The app runs under App Sandbox (`com.apple.security.app-sandbox`), which is what makes "no network" something the build cannot do rather than something it promises: with no network entitlement, `connect` and `getaddrinfo` are refused as `network-outbound`. The sandbox makes the app's home its container, `~/Library/Containers/ai.promptctl.low-talker/Data`, which is why the config file lives there. A file from before the sandbox, `~/.config/low-talker/config.toml`, is moved in when macOS creates the container at the first sandboxed launch, by the `container-migration.plist` the bundle carries. Two Mach names are excepted, each denied without it: the app registers its hotkey port (`ai.promptctl.low-talker.hotkey`) and looks up its input method's insert port.

The microphone takes `com.apple.security.device.audio-input`. Built with the runtime on and no entitlements, tccd logged `Prompting policy for hardened runtime; service: kTCCServiceMicrophone requires entitlement com.apple.security.device.audio-input but it is missing`. A Mac that already granted the microphone kept hearing. A Mac that never granted it would never be asked, and the app would hear nothing. Nothing else failed. Measured on 2026-09-16 on this Mac, both installations were built that way, and each transcribed "Hello world, this is Low Talker." from a fixture played at the microphone during a held chord.

An entitlement goes in only with the failure that needed it, written in the comment beside it in `project.yml`.

Every build is signed without `get-task-allow`, which Xcode would otherwise add to a build meant for debugging, and a hardened process without it refuses a debugger: `lldb` and Instruments cannot attach to the app. Read the unified log instead, as the sections below do. Every signature also carries a secure timestamp, which `codesign` fetches from Apple's timestamp server, so a build with no network fails to sign.

### Signing for release

    NOTARY_PROFILE=<profile> scripts/release dist ~/Library/Application\ Support/low-talker/hub   # dist/LowTalker-offline.pkg, dist/LowTalker-network.pkg

`scripts/release` is the whole release, two scripts run in order, each of which also runs alone:

    scripts/sign-release dist ~/Library/Application\ Support/low-talker/hub   # both packages, Developer ID signed
    NOTARY_PROFILE=<profile> scripts/notarize dist/LowTalker-offline.pkg        # notarized and stapled, one package at a time

Each package is signed, notarized and stapled once, and that one submission covers everything it installs: the notary service checks every signed bundle inside it. On a Mac with no network, a stapled ticket is the only way Gatekeeper can reach a verdict on the package, unless that Mac has already learned the ticket. `scripts/release` asks the profile to answer before the build starts, so a missing credential stops it in seconds rather than minutes. Every bundle carries the version `project.yml` sets, `MARKETING_VERSION` and a build number, `CURRENT_PROJECT_VERSION`, which is raised by hand before each release. Each bundle also carries `LTSourceRevision`, the commit it was built from, with a hash of the working tree appended when that tree differs from the commit. `scripts/source-revision` prints it, and `make app` passes it to the one `xcodebuild` call that builds both bundles. The build number is the same for every commit between two releases, so the revision is what tells two builds apart. The app sends words only to an input method that says the same number and revision in its greeting. It holds the words of any other build, says so on the status line, and names the fix, a reinstall. The Nth release is build N, so `scripts/release` refuses a built app whose build number is no higher than the number of release tags on origin's other commits (`v0.1.0-alpha.3`, the third, was build 3). A release is one tag, pushed first: before building, `scripts/release` requires exactly one `v*` tag on origin at the commit being built, naming `MARKETING_VERSION` (`v0.1.0` or `v0.1.0-alpha.7` for 0.1.0), on a commit of origin's master, with a clean working tree.

An offline check on the Mac that notarized a release cannot show that the staple works, because that Mac already knows the ticket. On 2026-09-23 a throwaway app was notarized and stapled, packed into a signed disk image, and the image notarized. One copy was stapled and one was not, and both were given a browser's quarantine. Then a pf anchor blocked every outbound connection except DNS and api.anthropic.com, which the agent running the test needed, and api.apple-cloudkit.com was confirmed unreachable. `spctl` accepted both copies as `source=Notarized Developer ID`, the unstapled one included, and it still did after `syspolicyd` was restarted. Notarizing and stapling here had taught this Mac the ticket, and the two copies share one code signature, so it covered both. The v0.1.0-alpha.3 release behaved the same way under the same block: `syspolicyd`'s ticket lookup timed out, the image mounted, and the app launched from `/Volumes/LowTalker` with no prompt. That shows only what this Mac already knew. `xcrun stapler validate` is not an offline check either: it asks CloudKit for the ticket and fails with error 68 when it cannot reach it, even on a stapled file. The staple is only proved by a Mac that has never looked the ticket up, opening the image with the network off.

That Mac was studious.local, an M1 Max Mac Studio on macOS 15.0.1 that had never run low-talker, on 2026-09-23. The same three images were copied to it and quarantined. A pf anchor there blocked every outbound connection except to the Mac driving the test over SSH, and api.apple-cloudkit.com and 1.1.1.1 were confirmed unreachable. With the network off, `spctl` rejected the unstapled probe image as `source=Unnotarized Developer ID` and accepted the stapled one, so the check tells a staple from no staple. It accepted the v0.1.0-alpha.3 image as `source=Notarized Developer ID`, and `syspolicyd`'s lookups at CloudKit timed out throughout. The image mounted in 2 s with no prompt. Opening the app out of it drew the confirmation macOS shows the first time any downloaded app opens: "“LowTalker” is an app downloaded from the Internet. Are you sure you want to open it?", adding "Apple checked it for malicious software and none was detected", with Open, Show Disk Image and Cancel. No developer can remove that dialog. It is not the "cannot be verified" warning, which is what a missing ticket produces. After Open, the app ran from `/Volumes/LowTalker`, and its first request was for the microphone.

`scripts/sign-release` runs `make package` once per variant, in one derived-data directory, with `SIGNING_IDENTITY` set to the `Developer ID Application` certificate for team 6R988MUU27, and that identity and the variant are all it changes about the build: `project.yml` has one build configuration, and it signs every build, a development one included, with Hardened Runtime and a secure timestamp and without `get-task-allow`, so a bundle built by `make app` differs from a shipped one of the same variant only in its certificate. The bundle carries the default model ("The model store" above), taken from the source the second argument names, as `model-tool download --from` reads it, or from huggingface.co when there is none, and the script requires `model-tool status` to find it whole inside the built bundle. The build goes into a derived-data directory made for the run and deleted after it, so a release is always a clean build. It then checks the app and every input method bundle built beside the app for what the notary service refuses: a signature that is not the team's Developer ID, no Hardened Runtime, no secure timestamp, or `get-task-allow`. The first of those it finds stops it with the binary named. A build with no input method bundle fails there too, rather than passing a check that ran zero times. It requires each package to be named for the variant it asked for, since the name is read off the app's signed entitlements, and prints each package it leaves in the output directory, the offline one first. A bundle signed with the development identity fails the first. The Developer ID certificate lives in the login keychain, and `codesign` signs with it without a prompt.

`scripts/notarize` takes the signed app or an installer package, submits it with `notarytool` under the keychain profile `NOTARY_PROFILE` names, waits, and prints the notary log when the answer is anything but Accepted. It then staples the ticket and requires Gatekeeper to assess the result as `source=Notarized Developer ID`. The profile is made once per Mac with `xcrun notarytool store-credentials <profile>`, from an Apple ID with an app-specific password or from an App Store Connect API key. This Mac's profile is `lowtalker-notary`, and submissions under it have been Accepted since 2026-09-16. A missing profile, a profile that does not exist, and a path that is neither an `.app` nor a `.pkg` each stop the script with a message.

Pushing a `v*` tag runs `scripts/release` on a GitHub runner (`.github/workflows/release.yml`) and publishes a release carrying both packages. The tag's annotation becomes the release notes, and a version with a hyphen, like `v0.1.0-alpha.7`, is marked a prerelease. The release restores the default model from a cache that each push to master fills once per model name and Hugging Face revision (`.github/workflows/model-cache.yml`), waiting for the tagged commit's run to finish, since a run for one tag cannot restore a cache saved for another, and fetches from huggingface.co whatever the cache lacks. Either way it fetches at the revision `model-tool revision` named, which the cache key carries, so a moved upstream is a new cache entry, never the old one kept until eviction. The credentials are repository secrets, set once with:

    DEVELOPER_ID_P12_PASSWORD=<password> NOTARY_PASSWORD=<app-specific password> scripts/release-secrets <identities.p12> <apple id>

The `.p12` holds both Developer ID identities, Application and Installer, exported together from the login keychain. Each is made on developer.apple.com from a certificate signing request, with "G2 Sub-CA" chosen: a release chains through Apple's G2 Developer ID intermediate, which `scripts/developer-id` names, and `scripts/release-secrets` refuses an identity issued under any other. Xcode's Manage Certificates issues under the previous intermediate (measured 2026-10-16), which itself expires on 2027-02-01, so no certificate under it signs past that date. Apple issues these certificates for 13 months, so the pair is replaced each year. The Apple ID and its app-specific password are the pair this Mac's own notary profile is stored from. The script proves each credential before it sets any secret. The runner keeps the credentials in a keychain file made for the run, and `NOTARY_KEYCHAIN` points `scripts/release` and `scripts/notarize` at the profile there.

The Homebrew cask (`brew install --cask promptctl/tap/low-talker`) installs the offline package. Its body is `cask/low-talker.rb`, and the tap's `Casks/low-talker.rb` in promptctl/homebrew-tap is that file with a release's version and sha256 filled in. Nothing moves it when a release is published: after one, run `scripts/update-cask <tap checkout> <version>`, commit what it writes and push the tap.

`scripts/make-pkg` builds the installer package from an app and its input method: the app goes to `/Applications` and the input method to `/Library/Input Methods`, both at fixed paths. Neither bundle is a pkgbuild bundle component, so the installer writes both as plain files. Every rule a bundle component carries broke an install: it goes wherever LaunchServices last saw the identifier (such as a copy in `DerivedData/`), it skips a bundle whose version on disk is not older (every rebuild of one version), it deletes the old bundle before writing, and the one action that writes in place skips a bundle not already on disk, so a fresh Mac got nothing. Every package, one of a development build included, is signed with the `Developer ID Installer` certificate for team 6R988MUU27, because an installer signature needs an installer identity and the self-signed development identity is not one. It names the package after the app and its variant, which `scripts/variant` reads off the app's signed entitlements: none of the sandbox's network keys is `offline`, the server key alone is `network`, and any other set fails the package. The script checks the package's signature and that it installs both bundles.

### The installer package

A package and not a disk image, because of App Sandbox, measured on studious on 2026-09-28. Every file a sandboxed app writes carries a quarantine it cannot remove, so the text input system refused an input method the app had copied into `~/Library/Input Methods`. An app copied out of a quarantined disk image could not start its nested helper. Files an installer package writes carry no quarantine.

The package's scripts (`scripts/pkg/preinstall` and `scripts/pkg/postinstall`, each with the names written in by `scripts/make-pkg` and the shared `scripts/pkg/functions`) retire what ran before, and write each step to `/var/log/install.log`. Before the payload is written, the preinstall asks the running app to quit and waits until it has ended, however long that takes. The quit places or holds the words of every press the app heard, decoding them with the model in its own bundle, and on a cold load that can take minutes. Stopping the app is also needed because an app from before the package copied its own input method into its user's `~/Library/Input Methods` and would copy it back. A wait the installer cuts off at its 600 s script limit fails the install before anything on disk has changed. Once the payload stands, the postinstall does the rest. LowTalker was once installed as two apps side by side, the second as `LowTalker Dev` under `ai.promptctl.low-talker.dev`; the postinstall stops and removes that app and its input method wherever it finds them in `/Applications` and `/Library/Input Methods`, so one app and one input source are left. Next it removes the input method copies from every home folder. For each person logged in, it registers both bundles with LaunchServices, which the installer does not do for plain files, and switches off every LowTalker input method whose bundle is installed nowhere, changing only `AppleEnabledThirdPartyInputSources` in their `com.apple.inputsources`. For every person, logged in or not, it then deletes each sandboxed process's input source cache (`com.apple.IntlDataCache.le*` in their `DARWIN_USER_CACHE_DIR`), since none of them sees a newly installed input method until its cache is rebuilt, and System Settings' Keyboard pane would refuse to switch it on. The folders in there that macOS closes even to their owner, such as WebKit's sandbox caches, it names in the log and passes over. Then it stops every process of the input method, which the text input system starts again from the new bundle on the next request for one. Last, it starts the app again for each user it was running for, and the app selects the input method. A step that fails for one person is logged and fails the install once every other step has run. The front app picks up the new input method at its next change of focus.

The package writes over the bundles in place rather than deleting them first. The text input system drops an input method whose bundle disappears, along with its switched-on state, and a bundle that reappears is a new input method it will not run until the next login. Measured on studious on 2026-09-29: with the default, every upgrade cost the enable alert and a logout; written over in place, the input method stayed switched on and selected with no prompt. A file that an older build had and a newer one lacks would stay behind and break the bundle's seal, so the postinstall removes every path the package does not carry, gives both bundles to root, since a bundle a person once wrote keeps its owner across a plain-file install, and fails the install if either does not verify.

Moving from a build before the package, which kept its input method in `~/Library/Input Methods`, is a new path to the text input system, and it costs that once: switch the input method on again in Set Up.

`syspolicy_check notary-submission` is no help on this Mac. It reports `Internal Xprotect Error` for this app, for the dev-signed build, and for a one-line Swift app signed the same way, while iTerm and Karabiner-Elements pass. So the notary service's answer is the one that counts.

### Starting over

To recreate the certificate, run `security delete-keychain lowtalker-dev.keychain`, which also takes it off the search list; the next build makes a new one. An identity in the login keychain is deleted in Keychain Access instead (My Certificates, with its private key). The new certificate is a new signature, so re-grant the app's permissions in System Settings.

This certificate is for local development only. Nobody trusts it and it cannot distribute the app; release builds sign with Developer ID instead, as "Signing for release" above describes.
